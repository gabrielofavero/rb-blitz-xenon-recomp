# ReXGlue v0.11.0 migration

**Status:** Planning only, 2026-11-17. Source comparison and disposable patch
replay completed; implementation, upgraded builds, native platform acceptance
and performance measurements have not started. The production SDK pin and patch
stack remain unchanged. Move this plan to `in-progress/` when implementation starts.

## 1. Target and requirements

Migrate directly from SDK commit
`c94f5ebdcb3c9d1a460ca48e04f9758448f8d518` to **v0.11.0**, commit
`a3e1d82678ca20d68d4837a8e9ee4652ff073745`. The target is the released version,
not a moving development branch. There is no intermediate v0.10.1 delivery.

| Requirement | Acceptance condition |
| --- | --- |
| R1: Reproducible SDK | The gitlink names the upstream release commit. Every retained SDK/dependency change replays from repository patches on a fresh checkout. No local-only SDK commits or unexplained SDK dirt. |
| R2: Behavior preservation | Preserve the current default and Ultimate targets, startup/preparation, settings, content/DLC, saves, menu music, achievements, input, rendering and recovery behavior. Inventory concurrent project changes again before porting. |
| R3: Platform preservation | Cover Windows and Linux AMD64/ARM64, macOS x86-64/arm64 and iOS arm64 at their existing support levels. Validate D3D12 on Windows and Vulkan on applicable desktop targets; preserve MoltenVK on Apple targets and both iOS launch routes. Record unavailable configurations explicitly. |
| R4: Measured performance | Compare the patched current SDK with the patched v0.11.0 build on matched workloads. Preserve downstream performance fixes; measure optional optimizations separately. No performance claim based solely on commit descriptions. |
| R5: Stable data and packaging | Preserve writable data locations, settings compatibility, imported assets, save/profile data, DLC and controller schemes. Update runtime packaging, dependency pins, licenses and cache compatibility deliberately. |
| R6: Reviewable delivery | Every original patch has a final disposition, replacement location, platform scope, consumer evidence and validation result. Update the standing patch ledger and build/toolchain documentation. |

Existing feature plans retain their scope. Framerate expansion, unrelated feature
work, new settings surfaces and new host overlays are outside this migration.

## 3. Implementation decisions

| Decision | Contract |
| --- | --- |
| D1: Exact release target | Pin v0.11.0's full upstream commit throughout the migration. Assess later SDK releases separately. |
| D2: Isolated migration | Use a separate branch/worktree or checkout with independent SDK working files and build directories. A parent worktree's submodule initialization must be checked explicitly. Preserve the current checkout and all unrelated uncommitted work. |
| D3: Port responsibilities | Start from pristine v0.11.0. Map moved code and changed APIs, retire proved upstream replacements, and regenerate patches in dependency order. Do not make the new SDK emulate every removed API through a permanent compatibility layer. Small title-owned adapters are appropriate where they reduce repeated coupling. |
| D4: Owning patches | Fold corrections into the patch that owns the behavior. Add a patch only for a distinct responsibility and record that boundary. Preserve original IDs in the lineage ledger, including retired and consolidated entries. No arbitrary patch-count target. |
| D5: Explicit platform boundaries | Declare scope for every patch before editing. Shared behavior stays shared; Apple, iOS, architecture and backend behavior is guarded at the responsible boundary. A Windows pass cannot validate POSIX faults, MoltenVK or an iOS lifecycle. |
| D6: Conservative performance defaults | First establish parity with v0.11.0 defaults and retained downstream fixes. Keep `forward_stack_stores` off initially; test it independently. Preserve the upstream fast vector-math defaults unless a demonstrated title correctness issue requires exact behavior. |
| D7: UI testing and presentation | Build current binaries before requesting game/UI testing. Before any manual or automated game navigation, ask whether the owner wants to perform it and wait for the answer, unless scoped autonomous UI authorization already exists. Continue independent builds and host tests while waiting. Existing authorized overlays may be retained; a new host overlay requires explicit authorization. |
| D8: Evidence before adoption | Buildable checkpoints may be saved during migration. Switch the delivery baseline only after strict replay, required builds/tests, packaging checks and regression review. Keep missing native evidence and owner UI acceptance visible. |

## 5. Execution sequence

Each stage records files changed, patch dispositions, commands/results and native
limitations in this plan. A stage's focused tests supplement the final full
build; no partial SDK assembly is presented as a working game.

### 5.1 Freeze the baseline and map dependencies

- Re-read repository instructions and inventory current SDK patches, consumers,
  project changes and target records. Capture the exact source snapshot used for
  comparison, including any intentionally included uncommitted changes.
- Create independent current-pin and migration checkouts/build outputs. Reproduce
  strict SDK/nested replay and build the current Windows Release baseline before
  any requested UI testing. Save test results and package/runtime manifests.
- Create an API/path map for application lifecycle, kernel objects/threads,
  memory, hooks/detours, settings/logging, filesystem/content, HID, audio and GPU.
- Resolve the Vulkan/MoltenVK dependency approach early. v0.11.0 expects the
  external Vulkan SDK, with Vulkan 1.4.313 normally and a 1.3.275 Linux ARM64
  exception. Record headers, loader, VMA and Apple library versions/hashes and
  required CMake target names. Verify the chosen sources on every target.
- Select a pinned patched MoltenVK source build for Apple if drawable ownership
  equivalence in an external binary cannot be proved. Keep its patch/application
  route reproducible and compatible with the iOS cross-build.

**Deliverable/gate:** baseline manifest and tests, complete API/patch map, and a
documented dependency/staging decision. No unresolved dependency strategy is
carried into Apple porting. Live baseline captures may wait for UI authorization.

### 5.2 Port build integration and code generation

- Pin the isolated migration SDK to the full v0.11.0 commit; initialize its exact
  dependencies. Preserve the project's flattened-symlink repair requirements.
- Replace the old `generated/rexglue.cmake` integration with the release's
  `rexglue_project`/target setup while retaining an explicit source-tree SDK
  route for downstream patches. Adapt `rex::runtime`, `rex::core` and combined
  GPU-plugin references to actual new module/driver targets and runtime files.
- Update `CMakeLists.txt`, presets, manifest SDK version, toolchain records,
  direct SDK source references in tests and staged helper tools. Keep exact-pin
  enforcement active; do not bypass it with an allow-other-toolchain switch.
- Reconcile the new Clang/AppleClang requirements and macOS 13.3 default with
  current target minima. Prove any retained lower floor; otherwise record and
  apply the raised minimum consistently in build, package and documentation.
- Port or retire 0005 and port 0075. Adapt generated image symbols, hook macros,
  registrar interfaces, PCH configuration and module import ABI. Regenerate all
  guest output rather than mixing old generated code with new runtime headers.
- Preserve first-configure codegen ordering, input/dependency invalidation,
  clean rebuild behavior and readable paths in diagnostics.

**Deliverable/gate:** build the migrated SDK tools and applicable upstream
codegen/PPC tests; generate the default target successfully and validate
registration coverage. A second unchanged generation/build must be a no-op;
changing a manifest/input must invalidate the expected output.

### 5.3 Port shared runtime, settings and content integration

- Adapt guest memory access, kernel state, threads, hooks/detours and import
  calls to the new interfaces. Audit direct struct/handle assumptions, guest
  register preservation, setjmp/longjmp and exceptions, TLS and ARM64 alignment.
- Port content/device hooks and menu-music ownership against the new filesystem.
  Keep save/profile paths, license handling, DLC discovery, validation, failed
  content recovery and refresh semantics stable for default and Ultimate data.
- Map cvars to new settings ownership without changing persisted IDs, precedence,
  CLI overrides, hot apply, restart markers or restore-profile behavior.
- Port session logging and diagnostics; keep bounded tracing available for the
  later matched comparisons. Evaluate the retirement candidates individually.

**Deliverable/gate:** migrated host suites for guest memory/runtime symbols,
settings storage/service/hot apply, local saves, content safety/discovery,
menu-music lifetime, logging and shutdown pass. Record tests that still depend
on graphics/application stages; close them before the final full-test gate.

### 5.4 Port graphics, preparation and audio

- Port fixed-point conversion, descriptor caches, texture overrides, packet
  recovery, D3D12 fence/readback, native caches and async completion handling to
  the new Xenos implementation. Preserve backend-specific failure paths.
- Port the preparation lifecycle, required guest payload gate, cancellation,
  boot painting and audio scheduling/handoff. Keep shader work off critical
  submission/audio paths as in the patched baseline.
- Port Apple shader lowering, portable storage, upload hazard tracking and queue
  policy with the correct backend/platform guards.
- Define cache identity/invalidation for shader translations, pipeline recipes
  and native driver blobs separately. Reuse only proved-compatible data; write
  new versions/namespaces or safely rebuild incompatible caches. Preserve user
  data and retain baseline cache snapshots for comparison.
- Retire 0033 only after validating upstream pipeline reuse. Keep 0034 until
  equivalent nonblocking submission behavior is demonstrated.

**Deliverable/gate:** graphics/preparation/audio tests in section 6 pass on the
available backends; delayed/concurrent pipeline completion, cache rejection,
cancellation, failure, shutdown and restart paths are covered. Translator and
cache version changes are documented and reproducible.

### 5.5 Port application, desktop UI and input

- Rework `src/rb_blitz_app.h` and `src/main.cpp` around `App`/`TitleApp`. Map
  configuration, launch/load gates, dialogs, restart, guest exit and teardown to
  their new ordering without duplicating initialization or starting a guest early.
- Port input activity filtering, keyboard/controller/mouse/touch switching,
  search keyboard, media/extra buttons, vibration and modal input capture through
  the new HID/UI services. Preserve title binding and icon semantics.
- Port display-mode intent, confirm/revert timing, pixel sizing, visible-region
  transforms, crop, HUD/touch mapping and existing authorized overlays.
- Keep themed keyboard, achievements, image textures and texture overrides
  connected to their production consumers; preserve settings layout constraints.

**Deliverable/gate:** complete Windows Release build and applicable host suites
pass. Record current-build owner/manual acceptance for startup, settings,
display recovery, input switching, content/music, saves and guest exit. Ask and
wait before driving UI under D7; host tests do not establish these observations.

### 5.6 Complete native platform integration

- Build and test Linux targets with matching Vulkan/loader/SDL dependencies and
  installed-package library resolution; preserve POSIX fault handling.
- Build macOS architectures separately. Port native window/surface ownership,
  skipped-paint recovery, drawable sizing, library/ICD discovery and relocatable
  bundle staging to the selected external/patched dependencies.
- Port iOS platform guards, cross-compiled SDK modules, native host tools,
  thread/signal behavior, suspension/resume/clock coordination, queue gates,
  drawable retention, portrait layout and accelerometer controls.
- Preserve both bundled-assets startup and the separate first-launch importer:
  missing/valid import, cancel, repair, successful import and later direct launch.
  Recheck initialization chaining and suspended/resumed preparation.

**Deliverable/gate:** update the platform matrix in section 6 with native build,
test, package and runtime evidence. Unavailable targets remain explicitly
unverified; required missing build/automated gates keep implementation in
progress. Any supported-OS-floor change is recorded consistently.

### 5.7 Prove replay, packaging and clean installation

- Regenerate the final ordered SDK patch stack against pristine v0.11.0. Update
  `patches/README.md` with all 71 old IDs, nested-patch lineage, replacements,
  removed APIs, platform scope and validation evidence.
- Update both setup appliers and nested audit rules for the selected dependency
  layout. Preserve atomic preflight, idempotence, drift rejection, edit protection
  and Windows CRLF compatibility. Run maintained replay tests and strict audits.
- Exercise a fresh clone/dependency initialization/patch/configure/codegen/build
  route and repeat patch application/checks. The parent gitlink must remain the
  exact upstream release; reject unexpected tracked or untracked SDK source.
- Stage all new module/driver and SDL shared libraries from explicit target
  outputs. Update Windows/Linux/macOS/iOS packaging, dependency pins, runtime
  allow-lists, loader paths, signing inputs and third-party notices.
- Run package/importer/distributable audits. Verify relocated launches, stable
  user-data paths and an update from the current package; importing and uninstall
  must preserve existing saves, profiles, schemes and user content.

**Deliverable/gate:** strict replay and applicable full test suites pass from a
fresh tree; packages contain the required native dependencies and no retail
assets or local build paths. CI runs the relevant replay and native build gates.

### 5.8 Measure performance and select defaults

Run the protocol in section 7 after functional parity. First compare the patched
current SDK to patched v0.11.0 with conservative defaults, then evaluate optional
stack forwarding independently. Attribute gains to measured stages, and fix or
disable a regressing optimization without removing unrelated correctness fixes.

**Deliverable/gate:** reproducible per-backend results and a recorded default
configuration. Explain material regressions and residual uncertainties before
switching the delivery baseline; do not label an unmeasured target faster.

### 5.9 Finalize documentation and delivery status

Update [build instructions](../../guides/build-and-run.md),
[toolchain records](../../guides/toolchain.md),
[distribution guidance](../../guides/distributable.md), affected engine/settings
records, platform READMEs and known issues. Keep historical measurements intact.
Run the documentation checker, inspect the complete diff, and record the final
SDK/dependency identities, patch count, builds/tests, performance results and
remaining owner UI checks. Move the plan to `finished/` only when its required
implementation/build/automated work is complete. Runtime release acceptance is

## 7. Performance acceptance protocol

1. Capture a current-pin baseline and a v0.11.0 candidate built from the same
   project feature snapshot, toolchain and optimization settings wherever the
   release requirements permit. Document unavoidable toolchain/dependency changes
   as confounders. Preserve baseline binaries and use separate data/cache copies.
2. Fix machine power mode, display, frame cap, resolution/render scale, backend,
   graphics settings, game variant, DLC library and song/segment. Compare at the
   current supported rate. Verify rendering/game behavior before timing.
3. Measure cold application caches and repeated warm runs separately. Control
   native driver cache state where possible and record it where not controllable.
   Include startup to guest-ready, post-start preparation, song load, steady
   gameplay and menu-music behavior during loading. Use at least five matched
   runs per workload/configuration and alternate build order to reduce drift.
4. Record CPU/GPU frame time where available, median/p95/p99 frame time, missed
   frame budget and worst stalls, pipeline creation/wait counts, preparation/load
   duration, audio underruns, process CPU time and peak memory. Compare equivalent
   trace settings; do not run one build with extra diagnostics and call it slower.
5. Compare default v0.11.0 first. Then regenerate/rebuild with
   `forward_stack_stores` enabled as a separate experiment. Check generated code,
   targeted PPC tests and guest behavior, including hook/exception boundaries.
   Do not bundle exact vector math or other settings changes into that comparison.
6. Treat a repeatable median or p95/p99 regression greater than 5% and larger
   than observed baseline variability as a required investigation. Investigate
   new frame-budget misses, severe stalls, audio underruns, visual differences,
   load failures or lifecycle faults regardless of percentage. Fix regressions
   or record a specific reviewed tradeoff before adoption; never average away a
   backend/platform failure. The 5% threshold is a planning gate, not a measurement.

Use existing tracing and diagnostics; no new host overlay is needed. FPS at a
fixed cap can hide CPU improvements, so include frame time and CPU headroom.
Startup gains do not establish steady-state gains, and reduced worker spinning
does not by itself establish higher framerate. Do not count the upstream Vulkan
paint-pipeline fix as a new gain over a baseline that already carries 0033.

## 8. Rollback and completion record

Keep the current patched release and its dependency/toolchain/cache manifests
available throughout migration. Before modifying persisted settings/cache formats,
retain compatible copies and define forward/backward behavior. Saves, profiles,
import manifests and game files must not be rewritten merely to test a new SDK.

If a gate fails, retain the isolated migration and its evidence, keep the current
delivery baseline, and correct the failing component. Restore a prior executable
with its matched runtime modules and cache namespace; mixing old and new SDK
libraries is not a valid rollback. A lower SDK release is outside this plan.
