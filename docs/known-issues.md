# Known issues and standing limitations

Enduring facts only. The **chronology** — what was tried, in what order, and what
the logs said — lives in [bringup-log.md](history/bringup-log.md); this file is the index
of things that are still true and will still be true next session.

Issue IDs (`B-00N`) are allocated in `history/bringup-log.md`. A merged or disproved issue
is removed from this file, not from the log.

| **B-006 (class; discovery causes fixed by patch 0005, one limit left)** | Functions found only through an indirect call — no PDATA, no static `bl`, or a hole inside a run of 8-byte adjuster thunks — were missing from the register table and surfaced at runtime as `[FATAL] Call to invalid or unregistered function at guest address 0x…`. The manual fix is still `[functions."0x…"]` (no `size`/`end`) in [config/functions.toml](../config/functions.toml) + codegen + rebuild, and the 24 forced entries (3 tail branches, 5 boot targets, `0x8278A6E0`, `0x827EC038`, 14 thunk-table holes) stay as the evidence trail. Since patch 0005 the discovery side is covered — `bctr` is a terminator and a region already registered is re-split when a later pass reveals a boundary inside it — measured with the list trimmed to the 3 oldest entries: codegen found **0 of the other 21** addresses before, **13** with the terminator alone, **20** with the fixpoint. The one left, `0x827EC038`, is a 24-byte leaf whose address is only taken in data, so no segment mentions it; it stays a forced entry. With the full list the table grew 38,365 → 38,439 entries and a previously separate 8-byte start (`0x826D8638`) correctly became the interior label of the function containing it (`0x826D8620`). A newly reached UI or gameplay path can still expose a hole, but it no longer has to. | [bringup-log.md](history/bringup-log.md) |
| **B-009 (resolved, then corrected)** | Music was silent because the `xboxkrnl` `XeKeysSetKey`/`XeKeysAesCbc` layer is a `REX_EXPORT_STUB` no-op in ReXGlue; [src/hooks/crypto.cpp](../src/hooks/crypto.cpp) intercepts both imports and forwards to `XeCryptAesKey`/`XeCryptAesCbc`. Corrected on 2026-09-19: the guest installs with a **constant key id** (`0xE0`) and carries the MOGG version in the *buffer offset* (`&table[GetEncMethod(version) * 16]`), so the plaintext entry selected by the offset is what must land in the slot. Music plays. That selection rule is now pinned by host unit tests ([tests/crypto_keytable_tests.cpp](../tests/crypto_keytable_tests.cpp)) that need no boot. | [bringup-log.md](history/bringup-log.md) B-009 |
| **B-010 (fix in place; two standing limits)** | 32-bit guest texture formats (`k_32`, `k_32_32`, `k_32_32_32_32`) with `num_format = 0` are 0.32 fixed point — they have no samplable host format, and without [patch 0002](../patches/rexglue-sdk/0002-32-bit-fixed-point-texture-conversion.patch) they sample `(0,0,0,0)` and make alpha-blended 3D invisible (this is what hid the note highway). The patch converts them on the CPU into an upload-pool staging buffer. Still true: `num_format = 1` (integer) textures fail to create, and one converted texture plus its mips must fit a single 2 MiB upload page (largest seen so far: 256 KB). | [bringup-log.md](history/bringup-log.md) B-010 |
| **Frame pacing and input polling have four standing limits** | (1) **One long stall per song survives tracing on**: the accepted vsync-on run has a single 1174.9 ms `VdSwap` gap (263.6 ms in `XE_SWAP`), the vsync-off run 254.3 / 245.8 ms; no threshold asserts on the maximum, and the 250 ms poll-gap bound is the one the tail actually approaches (142.1 ms and 243.5 ms). (2) **Injected keys depend on the game window holding the foreground**: `rexglue-sdk/src/input/mnk/mnk_input_driver.cpp` builds the pad state from the window's `WM_KEYDOWN`/`WM_KEYUP` and clears it on focus loss, so a press stolen by another window never reaches the guest. The driver samples the foreground across the whole hold and repeats an unclean press, and [scripts/audit_pacing_input.ps1](../scripts/audit_pacing_input.ps1) discards rather than asserts those, but the numbers are only as good as a machine left alone. (3) **A press shorter than a poll gap can be invisible**: of the three probes realized below 25 ms, two were seen and one fell between polls — that is how a polled pad behaves rather than a defect, and a human press is an order of magnitude longer. (4) **vsync off is host-load dependent**: the recorded run measures 68.3 fps where an earlier run of the same route (before the press-delivery change) measured 62.9 fps, so an uncapped frame rate is a property of that hour's machine as much as of the guest. | [bringup-log.md](history/bringup-log.md) "Close-out: frame pacing and input polling" |
| **Mouse navigation is a synthetic pad, with five standing limits** | The mouse drives the guest menus by emitting discrete **left-stick presses**, LMB = A and RMB = B, from [src/input/mouse_ui.cpp](../src/input/mouse_ui.cpp), installed as a third input device and gated by `mouse_ui_nav`. (1) **The selection is measured onto the pointer's row, and where it cannot be, travel stands in.** With `mouse_ui_hover` on (the default) the driver reads the guest's own frames back through `rex::ui::Presenter::CaptureGuestOutput`, differences the frame before a press against the frame after it to find the two positions of the highlight, and keeps pressing one row at a time until the measured row is the pointer's row — so an offset is not possible by construction, no per-screen pitch constant exists to be wrong, and the screens measured so far land exactly (main menu 26-27 px, HELP & OPTIONS 53 px, AUDIO/VIDEO screens 56 px per row). Measuring needs frames: on a guest whose output cannot be read back, or on a window whose client size and guest size are not both known yet, the driver is the older relative model — cumulative pointer travel into `round(distance / row)` presses with `mouse_ui_row_fraction` (0.0417, 32 px at 768) as the row, whose error *is* relative and grows with distance on a screen whose pitch differs (the song list's selectable rows are 96 px apart). (2) **A press is time, not polls.** The guest reads a pad hundreds of times a second while its menus advance on its own frame clock, so a hover's presses are held for a couple of the guest's frames and released for a couple more, timed from the rate the guest asks for the pad state at and floored at 60 Hz; a press shorter than one guest frame is invisible (it collapsed a 4-step drag into a single row) and a long one auto-repeats (the menus repeat under a held stick, ~one extra row per 275 ms, so 50 ms carries ~5× headroom). (3) **Menus, not gameplay, and never analog.** Hover moves in whole rows, so a 200 px drag is six discrete rows with nothing between them; steering and lane control are out of scope, and the right stick (`mnk_mouse`) is untouched. (4) **The guest never sees a cursor.** "Hover" means "the row highlight is put on the row the pointer is over", so pointer-over-element UI of the guest's own, per-pixel hit testing and 3D pick-by-cursor do not exist — and a screen whose rows a difference cannot read (no moving highlight at all) is one the aligner gives up on rather than presses blindly into. (5) **Travel and clicks are dropped, not queued**, while an ImGui overlay owns the pointer or the window is unfocused — a code path (`nav_.Reset()`), not an experiment: no live overlay was driven. Related and easily mistaken for a mouse fault: the runtime gates input on real window activation, so while the game is not the *foreground* window the menus ignore the mouse **and** the arrow keys until it is clicked back in front. | [bringup-log.md](history/bringup-log.md) "Mouse navigation" |

| **B-013: the Debug preset aborts the guest flow on an SDK assert** | Established by the clean-checkout smoke test of 2026-09-28 ([bringup-log.md](history/bringup-log.md)). On the first A at the title screen, while the guest enumerates content, a Debug runtime dialog appears — `MICROSOFT VISUAL C++ RUNTIME LIBRARY ASSERTION FAILED! … REXRUNTIMED.DLL … xam_info.cpp Line: 297 Expression: unk == 0` — and the route cannot continue. It is `XamAlloc_entry`'s `assert_true(unk == 0)`, and the parameter is unused by the implementation (`SystemHeapAlloc(size)` is all that happens), so **Release completes the same route** with the assert compiled out: the assert is Debug-only strictness, not behaviour the title depends on. The Debug preset still configures, builds (899 steps) and passes its host tests (6/6). Not fixed deliberately — the fix is a policy choice (relax guest-parameter asserts in Debug, or declare Debug a build/test-only preset and keep acceptance on Release) and Release runs the route with every assert compiled out, so a Debug run stops at the *first* assert it meets rather than showing there are no others. Acceptance evidence therefore comes from Release. | [bringup-log.md](history/bringup-log.md) B-013 |

## Accepted (by design, not bugs)

- Offline services stay honest `STUB`s — `XamVoiceSetMicArrayIdleUsers`,
  `XeKeysSetKey`, `XeKeysAesCbc` are **not** faked to success (B-009 is the one
  deliberate exception, and it is a real implementation, not a fake).
- 32-bit **integer** textures (`num_format = 1`) deliberately fail to create
  instead of being sampled as if they were normalized data: a wrong texture is
  harder to notice than a missing one. B-010's conversion covers
  `num_format = 0` (fixed point) only.
- A **corrupt settings payload is loaded as-is.** With
  `B13EBABEBABEBABE\5841122D\00000001\globaloptions\globaloptions` overwritten by
  `0xAB`, the title still reaches the offline menus, logs nothing about the
  content, and neither rejects nor rewrites the file (2026-09-20,
  `scripts/acceptance_persistence.ps1 -Only corrupt-payload`). A corrupt content
  **header** (`…\Headers\00000001\globaloptions.header`) is treated differently:
  the title recreates the 1024-byte default payload instead of reading it. Both
  stay non-fatal and leave the other content files alone. Nothing here is a
  bring-up shortcut — it is the title's own validation, which we neither add to
  nor emulate.
- `update:\gen\patch_xbox.hdr` → `0xc000000f`: no title update in this dump, and
  request that retail Blitz makes on every boot. (With an Ultimate payload
  installed this request is re-pointed at the merged `d:` view; see
  [ultimate-compat.md](ultimate-compat.md).)
- Three key/voice `STUB` warnings at boot.
- Online features (Rock Central sign-in, achievements, leaderboards, challenges, the
  online store — its `dlc_store` browse UI included — and DLC enumeration *by the
  service*) stay unavailable. That is the online half only: packages the user dumps
  load locally from the content root or from the DLC folder ([dlc.md](dlc.md)). This is **permanent, not a bring-up
  shortcut**: Blitz ships its own offline mode, so restoring online behaviour was
  never required for a playable port, and unblocking it is the community mod's job
  rather than ours. Our obligation is the opposite direction — the community's
  **Rock Band Blitz Ultimate** payload must keep working by drag-and-drop. What that
  means, which hazards an Ultimate payload brings (`update:`/TU5, overlay
  fingerprinting, replaced UI data), and what we refuse to ship are in
  [ultimate-compat.md](ultimate-compat.md).
- The project is **GPL-2.0-only**, deliberately not "or later": GPL-2.0 is what
  keeps us compatible with the GPL-2.0 Rock Band 3 recompilation project we adapt
  code from. Do not relicense, and do not add GPL-3.0-only or otherwise
  incompatible third-party code ([README.md](../README.md)).
- Borrowed code must carry provenance. Anything adapted from another project
  keeps its original license, says so in a header comment, and gets a row in the
  provenance table in [rb3-references.md](rb3-references.md) §9.
- The **build** refuses a `game/` that is not the fingerprinted dump, but a
  **runtime** game-data root that differs is only logged, never fatal: an Ultimate
  payload is a supported content variant chosen at launch
  (`--game_data_root`, `--ultimate_mode`), and refusing to start would turn
  compatibility into a bug report. `-DRBBLITZ_ALLOW_MODIFIED_GAME_DATA=ON` relaxes
  the build half for the same case — [build-and-run.md](build-and-run.md) §3,
  [ultimate-compat.md](ultimate-compat.md).
