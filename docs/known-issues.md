# Known issues and standing limitations

Enduring facts only. The **chronology** — what was tried, in what order, and what
the logs said — lives in [bringup-log.md](history/bringup-log.md); this file is the index
of things that are still true and will still be true next session.

Issue IDs (`B-00N`) are allocated in `history/bringup-log.md`. A merged or disproved issue
is removed from this file, not from the log.

| **B-006 (class; closed 2026-09-29 - no indirect-call entry is forced any more)** | Functions reached without a `bl` discovery can follow - no PDATA entry, a hole inside a run of 8-byte adjuster thunks, or an address no byte of the image mentions - were missing from the register table and surfaced as `[FATAL] Call to invalid or unregistered function at guest address 0x…`. Patch 0005 closed the discovery causes it could reach (`bctr` is a terminator, and a segmentation a later pass refines is re-split), and its gap fill was extended on 2026-09-29 to close the one it could not: the 24-byte comparator `0x827EC038`, which it now registers from the run of words no function's **extent** claims, when the word in front of the run leaves control. Its address appears nowhere in the decrypted image - no dword equals it in either byte order, aligned or not - and no direct branch reaches it, so the "address taken in data" reading of B-011 was wrong: the guest builds it in a register. The 21 entries of that class are **gone** from [config/functions.toml](../config/functions.toml). Measured: with the file trimmed to its 3 tail-branch entries, codegen registers all 21 addresses and the table holds 38,457 entries against 38,438 before the change (22 new, 4 absorbed - mis-split `li r3,imm; blr` epilogue fragments now interior to the function that owns them); a 40 s boot reached the title screen with no `[FATAL]` and `sub_827EC038` was called 206 times (measured with a temporary probe in its generated body), which is the call that used to trap. The three tail-branch entries stay: **one of them is still load-bearing** - with the file emptied to a comment, the Validate phase fails with `UnresolvedCall (1): 0x8243C688 from 0x8242A8DC: b 0x8243C688 from 0x8242A8DC - target not in any function`, because the instruction in front of `0x8243C688` is a `bl` and a call falls through, so the word after it is not an entry (codegen finds the other 23 of the historical 24 by itself). A newly reached UI or gameplay path can still expose a hole; the manual fix is unchanged - `[functions."0x…"]` (no `size`/`end`) + codegen + rebuild, with the address, the observed failure and the evidence recorded. | [bringup-log.md](history/bringup-log.md) |

| **B-010 (fix in place; one standing limit)** | 32-bit guest texture formats (`k_32`, `k_32_32`, `k_32_32_32_32`) are not floating-point — 0.32 fixed point when `num_format = 0`, 32-bit integers when `num_format = 1` — and have no samplable host format, so without [patch 0002](../patches/rexglue-sdk/0002-32-bit-fixed-point-texture-conversion.patch) they sample `(0,0,0,0)` and make alpha-blended 3D invisible (this is what hid the note highway). The patch converts them on the CPU, with the number format the fetch constant states (the fraction is scaled to the normalized range; the integer reaches the shaders unscaled, as in the SDK's vertex fetch and memory export, and its first use per format is logged), into an upload-pool staging buffer whose page the pool grows to fit the converted texture and its mips — the previous 2 MiB ceiling (largest conversion seen: 256 KB) is gone. Still true: the CPU mirror can be stale for GPU-written data, for which `d3d12_readback_resolve = true` is the escape hatch. | [bringup-log.md](history/bringup-log.md) B-010 |
| **Frame pacing and input polling have four standing limits** | (1) **One long stall per song survives tracing on**: the accepted vsync-on run has a single 1174.9 ms `VdSwap` gap (263.6 ms in `XE_SWAP`), the vsync-off run 254.3 / 245.8 ms; no threshold asserts on the maximum, and the 250 ms poll-gap bound is the one the tail actually approaches (142.1 ms and 243.5 ms). (2) **Injected keys depend on the game window holding the foreground**: `rexglue-sdk/src/input/mnk/mnk_input_driver.cpp` builds the pad state from the window's `WM_KEYDOWN`/`WM_KEYUP` and clears it on focus loss, so a press stolen by another window never reaches the guest. The driver samples the foreground across the whole hold and repeats an unclean press, and [scripts/audit_pacing_input.ps1](../scripts/audit_pacing_input.ps1) discards rather than asserts those, but the numbers are only as good as a machine left alone. (3) **A press shorter than a poll gap can be invisible**: of the three probes realized below 25 ms, two were seen and one fell between polls — that is how a polled pad behaves rather than a defect, and a human press is an order of magnitude longer. (4) **vsync off is host-load dependent**: the recorded run measures 68.3 fps where an earlier run of the same route (before the press-delivery change) measured 62.9 fps, so an uncapped frame rate is a property of that hour's machine as much as of the guest. | [bringup-log.md](history/bringup-log.md) "Close-out: frame pacing and input polling" |
| **Mouse navigation is a synthetic pad, with five standing limits** | The mouse drives the guest menus by emitting discrete **left-stick presses**, LMB = A and RMB = B, from [src/input/mouse_ui.cpp](../src/input/mouse_ui.cpp), installed as a third input device and gated by `mouse_ui_nav`. (1) **The selection is measured onto the pointer's row, and where it cannot be, travel stands in.** With `mouse_ui_hover` on (the default) the driver reads the guest's own frames back through `rex::ui::Presenter::CaptureGuestOutput`, differences the frame before a press against the frame after it to find the two positions of the highlight, and keeps pressing one row at a time until the measured row is the pointer's row — so an offset is not possible by construction, no per-screen pitch constant exists to be wrong, and the screens hovered so far land exactly (main menu 26-27 px, HELP & OPTIONS 53 px, AUDIO/VIDEO screens 56 px per row; MOD SETTINGS measures 40 px and the in-song pause menu's seven rows 37-38 px, measured from captures rather than hovered). Measuring needs frames: on a guest whose output cannot be read back, or on a window whose client size and guest size are not both known yet, the driver is the older relative model — cumulative pointer travel into `round(distance / row)` presses with `mouse_ui_row_fraction` (0.0417, 32 px at 768) as the row, whose error *is* relative and grows with distance on a screen whose pitch differs (the song list's selectable rows are 96 px apart). (2) **A press is time, not polls.** The guest reads a pad hundreds of times a second while its menus advance on its own frame clock, so a hover's presses are held for a couple of the guest's frames and released for a couple more, timed from the rate the guest asks for the pad state at and floored at 60 Hz; a press shorter than one guest frame is invisible (it collapsed a 4-step drag into a single row) and a long one auto-repeats (the menus repeat under a held stick, ~one extra row per 275 ms, so 50 ms carries ~5× headroom). (3) **Menus, not gameplay, and never analog.** Hover moves in whole rows, so a 200 px drag is six discrete rows with nothing between them; steering and lane control are out of scope, and the right stick (`mnk_mouse`) is untouched. (4) **The guest never sees a cursor.** "Hover" means "the row highlight is put on the row the pointer is over", so pointer-over-element UI of the guest's own, per-pixel hit testing and 3D pick-by-cursor do not exist — and a screen whose rows a difference cannot read at all (no moving highlight, or a move under the detector's colour threshold) is one the aligner gives up on rather than presses blindly into. A marker *at least as tall as its row* was in that class until 2026-10-01: its two positions overlap in the frame, so one difference holds a single band that neither the separated nor the merged path can place without a pitch. Two presses in the same direction place it — the band is rigid, so its shift is the pitch and what is left of it is the marker — which is what made the settings, pause and Ultimate-style lists (a wide bar at least as tall as its row) measurable instead of given up on. (5) **Travel and clicks are dropped, not queued**, while an ImGui overlay owns the pointer or the window is unfocused — a code path (`nav_.Reset()`), not an experiment: no live overlay was driven. Related and easily mistaken for a mouse fault: the runtime gates input on real window activation, so while the game is not the *foreground* window the menus ignore the mouse **and** the arrow keys until it is clicked back in front. | [bringup-log.md](history/bringup-log.md) "Mouse navigation" |

## Accepted (by design, not bugs)

- **The Debug preset runs the guest route, and Release is still the configuration acceptance
  runs on.** Until 2026-09-29 the Debug preset stopped at the first A on the title screen, on
  the SDK's `XamAlloc_entry` assert — a parameter the implementation never reads. It is not an
  unknown parameter: it is XAM's heap-flag word, and the call that aborted carried
  `flags=0x10000000` (heap selector 1, `HEAP_ZERO`-style bit clear), so the assert only made
  Debug refuse a call Release completes with every assert compiled out. Patch 0007 drops it
  ([bringup-log.md](history/bringup-log.md) "The Debug preset's assert policy") and Debug now
  walks the whole offline route, launch → a song → results, in 330 s against Release's 315 s.
  Release stays the acceptance configuration: it is the shipped artefact, and the SDK's
  remaining asserts are Debug-only strictness that only a route someone walks can clear.
- Offline services stay honest `STUB`s — `XamVoiceSetMicArrayIdleUsers`,
  `XeKeysSetKey`, `XeKeysAesCbc` are **not** faked to success (B-009 is the one
  deliberate exception, and it is a real implementation, not a fake).
- 32-bit **integer** textures (`num_format = 1`) are converted to *unscaled* integer
  values, not to normalized data, and the first use of each such format is logged
  (`REXGPU_WARN`). The `num_format` bit means here what it means in the SDK's other
  consumers of a number format: in the vertex fetch (`ucode.h`, `is_normalized() {
  return num_format_all == 0; }`) and in the memory export (`SurfaceNumberFormat`
  `kUnsignedInteger`/`kSignedInteger`, which clamp a component to its integer range
  while the fractions are scaled), an integer component reaches the shader as its
  own value. Until 2026-09-30 such a texture failed to create instead — which hides
  the content rather than showing it wrongly, and was kept because no title had been
  seen using it; the log line is what keeps the decision auditable now that the data
  is converted. No run recorded here has taken that path: the fetch constants this
  title samples were `num_format = 0` (the one B-010 decoded, and every conversion the
  runs logged).
- A **corrupt settings payload is loaded as-is.** With
  `B13EBABEBABEBABE\5841122D\00000001\globaloptions\globaloptions` overwritten by
  `0xAB`, the title still reaches the offline menus, logs nothing about the
  content, and neither rejects nor rewrites the file (2026-09-20,
  `scripts/acceptance_persistence.ps1 -Only corrupt-payload`). A corrupt content
  **header** (`…\Headers\00000001\globaloptions.header`) is treated differently:
  the title recreates the 1024-byte default payload instead of reading it. Both
  stay non-fatal and leave the other content files alone. Nothing here is a
  bring-up shortcut — it is the title's own validation, which we neither add to
  nor emulate.
- `update:\gen\patch_xbox.hdr` → `0xc000000f`: no title update in this dump, and
  request that retail Blitz makes on every boot. (With an Ultimate payload
  installed this request is re-pointed at the merged `d:` view; see
  [ultimate-compat.md](ultimate-compat.md).)
- Three key/voice `STUB` warnings at boot.
- Online features (Rock Central sign-in, achievements, leaderboards, challenges, the
  online store — its `dlc_store` browse UI included — and DLC enumeration *by the
  service*) stay unavailable. That is the online half only: packages the user dumps
  load locally from the content root or from the DLC folder ([dlc.md](dlc.md)). This is **permanent, not a bring-up
  shortcut**: Blitz ships its own offline mode, so restoring online behaviour was
  never required for a playable port, and unblocking it is the community mod's job
  rather than ours. Our obligation is the opposite direction — the community's
  **Rock Band Blitz Ultimate** payload must keep working by drag-and-drop. What that
  means, which hazards an Ultimate payload brings (`update:`/TU5, overlay
  fingerprinting, replaced UI data), and what we refuse to ship are in
  [ultimate-compat.md](ultimate-compat.md).
- The project is **GPL-2.0-only**, deliberately not "or later": GPL-2.0 is what
  keeps us compatible with the GPL-2.0 Rock Band 3 recompilation project we adapt
  code from. Do not relicense, and do not add GPL-3.0-only or otherwise
  incompatible third-party code ([README.md](../README.md)).
- Borrowed code must carry provenance. Anything adapted from another project
  keeps its original license, says so in a header comment, and gets a row in the
  provenance table in [rb3-references.md](rb3-references.md) §9.
- The **build** refuses a `game/` that is not the fingerprinted dump, but a
  **runtime** game-data root that differs is only logged, never fatal: an Ultimate
  payload is a supported content variant chosen at launch
  (`--game_data_root`, `--ultimate_mode`), and refusing to start would turn
  compatibility into a bug report. `-DRBBLITZ_ALLOW_MODIFIED_GAME_DATA=ON` relaxes
  the build half for the same case — [build-and-run.md](build-and-run.md) §3,
  [ultimate-compat.md](ultimate-compat.md).
- **A corrupt `default.xex` is refused by the loader, and the refusal says which claim does
  not fit.** B-014 was that the runtime identity check can only see an image the loader
  already accepted, so a corrupt copy was the loader's failure and the loader did not say
  so: the first 1 MiB of the recorded image (1,048,576 bytes of 9,023,488) ended the process
  with `0xC0000005`, the loader's own `Loading XEX image: game:\default.xex` as the last line
  written. The identity check stayed where it is; the loader's half is
  [patch 0008](../patches/rexglue-sdk/0008-xex-image-bounds-checks.patch). Every offset and
  length a XEX header supplies — the header size, the optional-header table, the security
  info and its page descriptors, the file format info and the block table of a
  basic-compressed image — is checked against the image's own length before anything reads
  through it, and the module loader refuses a file too short to hold a signature or to map.
  Three shapes, one line each, no identity line and a non-zero exit
  ([scripts/acceptance_wrong_data.ps1](../scripts/acceptance_wrong_data.ps1)):
  `truncated` (1 MiB) → `Refusing damaged XEX image …: its block table describes 9011200
  bytes of image data, the image holds 1036288 after its 12288-byte header`; `short` (2 KiB)
  → `its header claims 12288 bytes, the image holds 2048`; `empty` → `Failed to map … (0
  bytes) for module game:\default.xex`. Two standing limits: a **normal**-compressed image
  (`compression_type = 2`, which neither this title nor the Ultimate payload's own image is)
  describes its data as a chain in which each block names the length of the next, so it
  cannot be summed before it is read and a truncated one still walks the SDK's original
  de-block loop; and a refused boot ends with exit `0xC0000374` rather than 1, because the
  only path that runs the SDK's post-`Setup` teardown is the failure path (a normal exit
  hard-exits by design) and that teardown corrupts the heap — reproducible with a failure
  patch 0008 does not touch, `--game_data_root` pointing at an empty directory, which logs
  `Entrypoint XEX not found` and exits the same way. The build gate stays the half that
  covers the build — [bringup-log.md](history/bringup-log.md) B-014.
