## Accepted (by design, not bugs)

- **The game window is one size, and the player cannot drag it** (owner requirement, 2026-10-14). The
  window is a picture of one render size: `SettingsBoot::ApplyWindowPolicy` writes
  `video_mode_width/height` so the presenter scales the frame into a region of the frame's own shape,
  writes `window_width`/`window_height` only when the decorated window would not fit the display's
  usable area, and asks for `window_resizable = false` ([patch 0017](../../patches/rexglue-sdk/0017-fixed-size-window.patch)).
  It is a *limit* because a player used to resizing a window cannot, and because the size is decided
  before the window exists — a resolution or display-mode change is applied on the next boot, like
  every other graphics row. It is deliberate: an arbitrary client area is a shape the render size
  cannot fill, which is exactly the distortion part 3 of [graphics.md](../settings/graphics.md)
  removed. Nothing about the separate Controller Settings utility changes — it builds its own SDL
  window ([controller-settings/main.cpp](../../controller-settings/main.cpp)).
- **Two settings files, and the game's own wins at equal rank** (Controller Settings D3). Controller Settings
  keeps `launcher.toml` where D2 puts it, and what it manages reaches the game as command-line
  flags — every row the profile moved off its compiled default is passed as `--<key>=<value>`, and
  `[remap]` is read out of the file by the game itself. The game's own `rb_blitz.toml`, next to its
  executable, is loaded after the command line at config rank, so for any row Controller Settings does not
  pass the game's file is what the game will really use. That is deliberate: an in-game change made
  through the F4 overlay's *Save to config* must not be silently undone by Controller Settings. It is a
  *limit* because it means Controller Settings' value can be right and still not be the one in effect —
  and a user who changes a display setting in-game and then sees Controller Settings' own value is not
  looking at a bug. Controller Settings' answer is to say so (B4's badge, on every tab, with the value
  the game will use and a *Copy the effective value* action that writes Controller Settings' file and
  never the game's). Ordering, once, for the record: argv → `RBBLITZ_*` → `rb_blitz.toml` → the
  Controller Settings profile's `[settings]` rows → compiled defaults, with the profile and `rb_blitz.toml` at
  the same rank and the game's file applied second. (`--dump-profile` prints every badged row, which
  is the audit for this rule without a screenshot.)
  **Measured 2026-10-05 (E3), fixed 2026-10-07:** the profile was *not* applied at all, so a game
  started **without** Controller Settings (its own shortcut, or a double-click) saw `rb_blitz.toml` and the
  compiled defaults and none of Controller Settings' rows. D3's rank 4 now exists: the game applies the
  profile's `[settings]` table at config rank before the SDK loads its own `rb_blitz.toml`
  (`src/profile/profile_apply.cpp`; `rex::cvar::SetFlagFromConfig`, SDK patch `0013`), so the rows
  reach a standalone launch too. The *limit* above still stands for a row the game's own file names:
  that file wins at equal rank, by design.
  [launcher-plan.md](../plans/finished/2026-09-27-launcher-plan.md) §11.6 records the measurement and the resolution, and
  `rb_blitz_controller_settings.exe --print-command` is still the way to see exactly what Controller Settings launch
  passes.
- **Controller Settings ships no cover art, and the installer's cover image is not committed** (Controller Settings
  D11/D15). Both are the same fact: the artwork is not ours to license, so nothing is redistributed
  with either binary. The installer's large wizard image is *generated* on the build machine by
  `installer/tools/make_art.ps1` and is never committed — the script's rule, and `build.ps1` treats a
  failed download as a warning rather than a build failure, so absence is the ordinary case. The
  Controller Settings has no cover at all yet: the General tab is a flat panel with the badge and the title, and
  drawing a ladder beside the tabs is A4, which owes the same absence-is-supported rule for its own
  art. Four images *are* committed under `assets/icon/` — `blitz.ico` (compiled into the game's exe by
  its `.rc`), `blitz-mono.ico` (Controller Settings' exe icon, the black-and-white alt), and the
  `blitz.png` / `blitz-mono.png` badges (the colour one is the wizard's) — and they are the app's own,
  which is what keeps `tracked-tree`'s "no binary artefact" claim true; see
  [distributable.md](../guides/distributable.md) for the packaging rows that cover the rest.
- **Controller Settings and the game can be different builds, and only some of the seam is versioned**
  (Controller Settings D2/C3, R-skew). Installed together they always match; the skew matters when one of the
  two files is replaced by hand, or a payload is dropped over an older install. What is *safe* is
  the part that was built for it: `[remap]` rows a build does not understand are kept verbatim and
  left alone rather than half-applied (`src/profile/remap.cpp`), a profile whose `schema_version`
  is newer is refused with a reason instead of reinterpreted (`src/profile/profile.cpp`, and the
  Controller Settings then refuses to save over the file), and an `--flag` neither build knows is *logged* as an
  unclaimed cvar — the cvar registry is finalized last so that report is trustworthy
  (`patches/rexglue-sdk/0009-log-levels-table-not-cvars.patch`). What is *not* covered: a cvar that a
  newer build renamed simply stops being passed, and the log's only trace of it is that unclaimed-key
  line; and the command line is strings on both sides, so no version handshake exists beyond the
  profile's own. Evidence: `scripts/acceptance_controller_settings.ps1`'s legs prove the shared half end to end
  (a `[remap]` row written by Controller Settings is the game's `remap: 1 pad control(s) rebound by the
  Controller Settings profile` line), and `--print-command` is Controller Settings' half of the contract.
- **The General tab's two path rows are stored twice, and only one of the two stores is passed on**
  (Controller Settings B1/B4/B7; measured 2026-10-05, E3). `Save game location` and `DLC location` are written
  by the panel into `[launch] user_data_dir` / `dlc_dir`, which is also what `--dump-general`
  reports; the launch command builds `--user_data_root` / `--dlc_root` from `[settings]
  user_data_root` / `dlc_root` (`controller-settings/src/game_launch.cpp`, `RowValue`). A profile whose two
  halves were made to disagree printed `row dlc_root = (empty)` from the panel while the command line
  carried `--dlc_root="D:\…\game\dlc"`, so a folder picked in the panel is shown by the panel and
  never reaches the game. [launcher-plan.md](../plans/finished/2026-09-27-launcher-plan.md) §11.7 has the reproduction and
  the (small) fix, which belongs with the row's storage rather than with the acceptance run that
  found it. Editing `[settings]` by hand is the current way to make the DLC or save folder travel.
- **R6 mouse mode is reported in the enhancement boot log** as `mouse_ui_nav`; the old unconditional mouse-driver boot message was removed.
- **Controller Settings' declared limits, as of A1/B1/B4/A3/A2.** (1) The badge's *Copy the effective value*
  button is reachable by mouse only: a second focusable target per row is a change to the focus
  model, and a pad binding for it belongs with A5; the row can be set to the same value by hand
  from the pad or the keyboard in the meantime. (2) Controller Settings' 200 %-DPI leg is unmeasured —
  the machine that verified A1 runs at 100 %, so DPI-aware layout is scaled but not eyeballed at
  a second step. (3) A successful pick in the folder, import and export dialogs was driven by
  hand (typing the path), not by the observation harness; the open-and-cancel half is scripted.
  (4) A save is explicit: the window size is kept on the way out (A1), and everything a row or a
  badge changed is written when *Save* is pressed, so a change can be reconsidered first — the tab
  strip says "unsaved changes" while one is pending. (5) **The bar's three actions are mouse-only on
  the keyboard**: a pad can launch (`Start`) and leave (`B`, `Back`), but *Save* has no key and the
  bar is not part of any tab's ring — putting it there is a focus-model change, and A5 is the prompt
  that owns "usable with the keyboard only". (6) **A long tooltip loses its tail**: the bar reserves
  two lines and cuts at a word with an ellipsis rather than growing, because the body was given the
  rest of the window before the bar was drawn. (7) **The pad's tuning is fixed**: an 8000 deadzone
  and a 0.45 s/0.12 s repeat, both constants rather than rows (C1 owns making them settings), and
  with two pads attached their state is merged rather than chosen between — which is D17's answer,
  and the bar's button names follow the last pad used, so the hints can change under a user holding
  two pads of different families. (8) **A pad's buttons were pressed by SDL's virtual joystick, not
  by hand**: `--test-pad` is the hook (`controller-settings/src/virtual_pad.h`), a real XInput pad was attached
  and opened throughout but never pressed, so "a hand press on real hardware" is the manual pass's
  (§6 wave 4). (9) A window that is restored or moved reads as the pointer having moved, because the
  pointer's window-relative position changes — the hints then say key names until the pad is used
  again. It is cosmetic and only visible while something resizes the window.

- **Every build directory writes the same generated settings header.**
  `controller-settings/out/generated/settings_table.h` is a fixed source-tree path (`controller-settings/CMakeLists.txt`,
  P0.2), so a tree configured with different backends overwrites the other's copy and the *last*
  build to regenerate decides what *every* binary offers — measured on 2026-10-05: the Release tree
  offers `Renderer = d3d12, vulkan`, and a Debug build (which had `REXGLUE_USE_VULKAN=OFF`)
  regenerating the shared file leaves the Release binary offering `d3d12` alone until it is rebuilt.
  The build does not notice, because the custom command's inputs did not change. Workaround: build the
  tree whose backends you want last, or re-run it by hand —
  `rb_blitz_embed_settings.exe --settings controller-settings/config/settings.toml --header controller-settings/out/generated/settings_table.h --backends=d3d12,vulkan`
  — and check with `--dump-layout`, which prints each enum row's choices. Making the header
  per-build-directory is a change to P0.2's contract, not a bug fix. **Mitigated 2026-10-13:** every
  Windows preset now sets `REXGLUE_USE_VULKAN=ON` (it is in `windows-base`), so the two trees offer
  the same `d3d12, vulkan` list and overwriting the shared header changes nothing; the mechanism is
  still there for any future flag that differs between trees.

- **The Renderer row is the build's; what actually renders is the machine's** (Controller Settings D18, B2/B3).
  The row's choices come from CMake (`choices_from = "gpu_backends"`), so Controller Settings can only offer
  what the binary beside it was compiled with — this Release tree offers D3D12 and Vulkan, a
  D3D12-only build offers one — and choosing one is a request the *driver* answers: the game's own
  log is where the answer appears (`DXGI adapter: AMD Radeon(TM) Graphics (vendor 0x1002, device
  0x163F)`, the D3D12 feature table, the shader and pipeline counts), not the row. So a machine whose
  driver rejects a backend fails at boot with the game's own message rather than at the row, and the
  two build trees sharing one generated settings header (the bullet above) can leave the row offering
  a backend the binary in front of you was not built with. Not a bug — enumerating a driver's
  capabilities means doing the GPU work the game does — but it is why a support report needs the
  game's log and `--dump-display` rather than a screenshot of the row.

- **The Debug preset runs the guest route, and Release is still the configuration acceptance
  runs on.** Until 2026-09-29 the Debug preset stopped at the first A on the title screen, on
  the SDK's `XamAlloc_entry` assert — a parameter the implementation never reads. It is not an
  unknown parameter: it is XAM's heap-flag word, and the call that aborted carried
  `flags=0x10000000` (heap selector 1, `HEAP_ZERO`-style bit clear), so the assert only made
  Debug refuse a call Release completes with every assert compiled out. Patch 0007 drops it
  ([bringup-log.md](../history/bringup-log.md) "The Debug preset's assert policy") and Debug now
  walks the whole offline route, launch → a song → results, in 330 s against Release's 315 s.
  Release stays the acceptance configuration: it is the shipped artefact, and the SDK's
  remaining asserts are Debug-only strictness that only a route someone walks can clear.
- Offline services stay honest `STUB`s — `XamVoiceSetMicArrayIdleUsers`,
  `XeKeysSetKey`, `XeKeysAesCbc` are **not** faked to success (B-009 is the one
  deliberate exception, and it is a real implementation, not a fake).
- 32-bit **integer** textures (`num_format = 1`) are converted to *unscaled* integer
  values, not to normalized data, and the first use of each such format is logged
  (`REXGPU_WARN`). The `num_format` bit means here what it means in the SDK's other
  consumers of a number format: in the vertex fetch (`ucode.h`, `is_normalized() {
  return num_format_all == 0; }`) and in the memory export (`SurfaceNumberFormat`
  `kUnsignedInteger`/`kSignedInteger`, which clamp a component to its integer range
  while the fractions are scaled), an integer component reaches the shader as its
  own value. Until 2026-09-30 such a texture failed to create instead — which hides
  the content rather than showing it wrongly, and was kept because no title had been
  seen using it; the log line is what keeps the decision auditable now that the data
  is converted. No run recorded here has taken that path: the fetch constants this
  title samples were `num_format = 0` (the one B-010 decoded, and every conversion the
  runs logged).
- A **corrupt settings payload is loaded as-is.** With
  `B13EBABEBABEBABE\5841122D\00000001\globaloptions\globaloptions` overwritten by
  `0xAB`, the title still reaches the offline menus, logs nothing about the
  content, and neither rejects nor rewrites the file (2026-09-20,
  `scripts/acceptance_persistence.ps1 -Only corrupt-payload`). A corrupt content
  **header** (`…\Headers\00000001\globaloptions.header`) is treated differently:
  the title recreates the 1024-byte default payload instead of reading it. Both
  stay non-fatal and leave the other content files alone. Nothing here is a
  bring-up shortcut — it is the title's own validation, which we neither add to
  nor emulate.

- **A corrupt `default.xex` is refused by the loader, and the refusal says which claim does
  not fit.** B-014 was that the runtime identity check can only see an image the loader
  already accepted, so a corrupt copy was the loader's failure and the loader did not say
  so: the first 1 MiB of the recorded image (1,048,576 bytes of 9,023,488) ended the process
  with `0xC0000005`, the loader's own `Loading XEX image: game:\default.xex` as the last line
  written. The identity check stayed where it is; the loader's half is
  [patch 0008](../../patches/rexglue-sdk/0008-xex-image-bounds-checks.patch). Every offset and
  length a XEX header supplies — the header size, the optional-header table, the security
  info and its page descriptors, the file format info and the block table of a
  basic-compressed image — is checked against the image's own length before anything reads
  through it, and the module loader refuses a file too short to hold a signature or to map.
  Three shapes, one line each, no identity line and a non-zero exit
  ([scripts/acceptance_wrong_data.ps1](../../scripts/acceptance_wrong_data.ps1)):
  `truncated` (1 MiB) → `Refusing damaged XEX image …: its block table describes 9011200
  bytes of image data, the image holds 1036288 after its 12288-byte header`; `short` (2 KiB)
  → `its header claims 12288 bytes, the image holds 2048`; `empty` → `Failed to map … (0
  bytes) for module game:\default.xex`. Two standing limits: a **normal**-compressed image
  (`compression_type = 2`, which neither this title nor the Ultimate payload's own image is)
  describes its data as a chain in which each block names the length of the next, so it
  cannot be summed before it is read and a truncated one still walks the SDK's original
  de-block loop; and a refused boot ends with exit `0xC0000374` rather than 1, because the
  only path that runs the SDK's post-`Setup` teardown is the failure path (a normal exit
  hard-exits by design) and that teardown corrupts the heap — reproducible with a failure
  patch 0008 does not touch, `--game_data_root` pointing at an empty directory, which logs
  `Entrypoint XEX not found` and exits the same way. The build gate stays the half that
  covers the build — [bringup-log.md](../history/bringup-log.md) B-014.
